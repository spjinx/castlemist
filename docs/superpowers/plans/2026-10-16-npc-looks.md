# NPC Looks Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Race-body NPCs export dressed: body, face, hair, armour, dyes, colours and body shape, all taken from the composite file's variants.

**Architecture:**
- Extend `format/composite` additively to read `raceSexData[].variants`.
- In the npc layer, read each character's look records and map a variant onto the Character Ripper's existing inputs (`CharacterManifest` + `AssemblyOptions`).
- `export_npc` then writes body.glb with `ripper::assemble_character`.

**Tech Stack:** C++20, castlemist format/npc/ripper layers, test framework `CM_TEST`.

**Spec:** `docs/superpowers/specs/2026-10-16-npc-looks-design.md` (binding).

## Global Constraints

- Composite parser changes are **additive only**:
  - new `CompositeVariant`, `VariantComponent` and `VariantColor` types;
  - new fields `CompositeRace::variants` and `CompositeRace::variant_ref_race`;
  - no existing field, name or behaviour changes;
  - the existing `tests/test_format_composite.cpp` tests pass unmodified.
- Do not modify content_map, content_schema, content_store, type_names, or any existing label or name. CLI output may gain fields.
- Never read Gw2.dat directly; use gw2dat_cli. Build and test only through `scratchpad/cmbuild.sh`.
- Variant layout (`PackCompositeVariantV20`, 64-bit packfile; array_ptr = `{u32 count, i64 self-relative ptr}`):
  - `token: u64`
  - `boneScaleIndex: u32`
  - `components: array_ptr<{nameToken: u64, color0..3: Color}>`
  - `eyeColor, hairColor, hairColor2, patternColor, skinColor: Color`
  - `skinIndex: u32`, `skinStyle: u32`
  - Color = `{u8 brightness, contrast, hue, saturation, lightness}`.

  Read the field order and packing from how `parse_composite` already walks `PackCompositeRaceDataV20`. The template lists `variantRefRace` (u64) and then `variants` after `type`, before `animOverrides`. Confirm the packing (structs are tightly packed in this file family) against real data: the variant count must match the number of 32-byte look records referencing that race.
- Look record: 32 bytes `{race token u64, look token u64, flags u64, 0}`. The race token must match the existing race regex.
- Armour piece types: 8 Boots, 9 Coat, 10 Gloves, 11 Helm, 12 Leggings, 13 HelmAquatic, 14 Shoulders.
- Cache version 3.

## Review Focus

- A look token not found in its race (24 of 3 805 cases): a note, no body.glb, no crash. Test `missing_variant_is_a_note`.
- `sylvarifemal` (truncated race token) must resolve to SylvariFemale. Test `truncated_race_token_resolves`.
- A component token that is neither armour nor face/hair/ears: a note, ignored. Test in Task 3.
- An NPC with several looks: `--look N` out of range gives a clear CLI error. Task 4.
- Colours: on, by ruling, using the measured mapping (79.3% exact palette match, recorded in the spec's "Colour bytes"); `kColorsNote` says so. Task 3.

```cpp
struct VariantColor { uint8_t brightness = 0, contrast = 0, hue = 0, saturation = 0, lightness = 0; };

struct CompositeVariant {
    uint64_t token = 0; uint32_t bone_scale_index = 0; std::vector<VariantComponent> components;
    VariantColor eye, hair, hair2, pattern, skin; uint32_t skin_index = 0, skin_style = 0;

// CompositeRace gains: uint64_t variant_ref_race = 0; std::vector<CompositeVariant> variants;
```

### Task 3: Variant → assembly inputs, with measured colours

**Interfaces — Produces:**

```cpp
std::optional<character::DyeShift> variant_color_shift(const composite::VariantColor&);                  // the measured mapping (colours on, by ruling)
```
- [ ] **Step 1: Measure the colour format.**
  - Add a temporary CLI subcommand `composite-colors` that prints, for one race, every variant component colour byte-tuple. Keep it as a documented research command, like `animmach`.
  - The content map's palettes (`cmap::palette`) give every dye colour's float `ColorShift`.
  - Test candidate mappings and pick the one under which the most (measured: 79.3%) of non-zero byte tuples equal the quantised shift of some palette colour:
    - (a) `b/255`-style scaling per field;
    - (b) signed bytes;
    - (c) the ranges the palette floats actually span: brightness ≈ ±128, contrast ≈ 0..2, hue ≈ 0..360, saturation ≈ 0..2, lightness ≈ 0..2.
  - Write the measured result (mapping, hit rate) into the spec's "Colour bytes" section.
  - By ruling the colours are applied with the best mapping (79.3% exact palette match, not 90%); `npc_assembly` adds `kColorsNote` instead of leaving tints off.
